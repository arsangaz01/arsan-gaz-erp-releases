# Arsan Gaz Telegram Copilot Bridge

This VS Code extension activates after VS Code startup so bridge readiness does not depend on the `workspaceContains` scan completing in a large workspace. It reports a waiting status in unrelated VS Code windows, but writes the shared heartbeat and processes inbox requests only when an `ArsanGazERP.csproj` or `ArsanGazERP.sln` project is open. It forwards requests from the AgentWatcher local inbox into the open VS Code Chat using `workbench.action.chat.open`. AgentWatcher creates inbox requests only after TelegramBotService validates the configured Telegram chat ID. Source version `0.2.18` uses bridge protocol `2`; AgentWatcher rejects older protocols and waits while the heartbeat reports an unresolved delivery.

The extension requires an open VS Code workspace that contains `ArsanGazERP.csproj`/`.sln` either at the root or up to two subfolders below the root, and the VS Code Chat command must be available. It opens the Chat view when the ERP workspace is opened, refreshes readiness when workspace folders change, reports readiness in the status bar, and writes a short-lived heartbeat for AgentWatcher. AgentWatcher waits indefinitely for readiness during VS Code startup and reuses an existing VS Code window instead of opening another one. When AgentWatcher launches VS Code for a Telegram request, it detects installed extensions with `*` or `onStartupFinished` activation and starts that session with those extensions disabled (excluding this bridge and GitHub Copilot). The user can explicitly enable any needed extension from VS Code's Extensions panel. This is a per-launch safeguard, not a persistent change to the VS Code profile; it does not alter an already-running VS Code process or manually launched sessions. The readiness check does not verify Copilot sign-in, entitlement, or model availability; those remain prerequisites. Queued commands, result waits, and user approvals have no elapsed-time expiry. Explicit cancellation and actual connection or processing failures remain reportable.

The bridge submits requests in Copilot Agent mode, which sends the prompt rather than leaving it as a draft. The Copilot prompt contains only the exact Telegram message body; task identifiers and any prior conversation context are not included. AgentWatcher may retain up to six recent completed turns as local task context for other processing, and `/yeni` starts a fresh context without deleting task history. A `/yanit <task-id> <message>` follow-up keeps the original task provider.

Agent-sourced recommendations and other non-Telegram workflows are different from original Telegram messages. AgentWatcher stores their complete, sanitized scope, criteria, and untrusted source evidence in a request-correlated local workflow contract. A Gözcü/Ar-Ge recommendation is automatically queued only when its final non-empty report line is exactly `ACTIONABLE: yes`, it includes a public HTTP(S) citation, automatic forwarding is enabled, and a local-day limit of six has not been reached. Missing, invalid, or `ACTIONABLE: no` decisions remain local. Disabling automatic forwarding restores per-item approval. Automatic forwarding is not user approval and does not accept completion criteria or bypass VS Code tool confirmations. The workflow's bridge `Text` asks Copilot to read its contract. The bridge still forwards `Text` verbatim and does not insert legacy `Context` into Telegram requests. A generic recommendation title, a submitted acknowledgement, or a visible queued prompt does not prove that the workflow has executed or completed.

When automatic forwarding is disabled, an explicit local user can approve one existing proposal with `ArsanGazERP.AgentWatcher.exe --approve-workflow <id>` only while the Watcher is stopped. The command uses the same sealed-contract and configured-chat owner checks as `/workflow-onay`; the normal Watcher must then be restarted. There is no blanket approval or automatic acceptance of completion criteria, and VS Code tool approvals remain user-controlled.

Completion requires evidence from the explicitly authorized local Copilot session event log. The observer starts at the current end of the log, matches the exact submitted root prompt, excludes subagent events, and accepts either a root `session.task_complete` event or a root `assistant.turn_end` following a root assistant message with no pending tool requests. That message may carry the `final_answer` phase or omit a phase. ISO timestamps and Turkish day-first UTC timestamps are parsed explicitly so locale formatting cannot make current events appear older than the authorization boundary. The turn-end fallback is accepted only after a three-second settling interval with no subsequent event or unread log data. A task summary takes precedence over an earlier candidate final response. A clipboard snapshot, stable text, a dispatch acknowledgment, and an approval response are not completion evidence. Changed authorization, a switched root prompt, a truncated log, or an observed processing error fails explicitly rather than returning an unrelated answer. The dispatch and observed session must be correlated; the presence of a heartbeat alone does not prove this. Switching conversations during an active Telegram command is not supported.

Telegram message bodies are retained verbatim through inbox serialization and Copilot prompt construction, including leading/trailing whitespace and line breaks. No framing text, task metadata, or conversation history is prepended or appended to the Copilot prompt. A slash-command token and its first separating whitespace are command syntax; the remaining argument is passed without trimming. Direct requests are limited to 4096 characters and are rejected explicitly if longer. Final Copilot response text is likewise preserved exactly; Telegram messages over its per-message limit are sent in ordered chunks whose concatenation is unchanged.

Authorized Telegram commands are saved before processing, without routine received, queued, or started notifications. Final task results and actionable failures remain deliverable; transport retries and queue waits do not expire tasks. A verified Copilot start is logged locally. Pending Telegram commands take priority over approved agent workflows across both inbox roots, with arrival-time ordering within each class. Priority is derived from local request/task identifiers, never message text. All inbox dispatch locks are held until the active request completes or fails, including while awaiting an approval or question response. Another bridge window cannot dispatch from the other inbox concurrently. Priority does not interrupt an already-started job, cancel an approval, merge messages, or replay historical ERP queue entries. An uncertain in-flight result after restart pauses dispatch for review instead of blindly replaying the command.

Explicit active-work additions are not implemented by this bridge. `/ek` is rejected with a failed acknowledgment rather than dispatched as an independent command. An addition must not be reported as merged until a supported in-flight steering interface and its target-session correlation are verified.

Dispatch also waits for verified completion in the authorized session before starting pending work, including work received during a manually started Copilot turn. The readiness observer reads a bounded tail once, then reads new bytes incrementally. A root `session.task_complete` or a settled root `assistant.turn_end` after a final answer with no tool requests establishes completion; a candidate final answer by itself, subagent completion, unread backlog, unfinished event, or unknown state does not. Authorization or log errors pause dispatch and are logged; requests remain on disk. This is a conservative bridge-side wait, not delivery into Copilot's native pending-message queue, and does not establish that the last-focused Chat widget is the authorized session.

Before invoking the Chat command, the bridge persists a dispatch-intent marker. A submitted acknowledgment is written only after the command returns successfully. A restart with an intent or acknowledgment but no correlated completion or recorded pre-submission failure pauses both inboxes, even when the request file was removed by an older bridge. Any stale uncertain dispatch that remains unresolved for 30 minutes is recorded as interrupted with error code `uncertain_stale`, then removed without replay; duplicate request copies with the same ID are removed from both inbox roots, and younger uncertain dispatches remain blocked. Once submission has been attempted, a command, observation, or persistence error preserves the intent and request instead of recording a definitive failure that would release following work. An intent requires a completion with the exact request/task IDs and a valid timestamp at or after dispatch; a failed acknowledgment cannot clear that intent. Legacy records without an intent remain readable, but a failed acknowledgment requires a nonempty error and valid timestamp. A failed acknowledgment is reserved for errors before submission. Failed acknowledgment persistence leaves the request intact. A progress-write error cannot replace an independently persisted completion with a failed acknowledgment. Recovery never replays an uncertain command, and unrelated requests can proceed after a stale delivery is quarantined.

The configured event-log session ID is an authorization boundary, not an automatically discovered active-chat identity. The host session URI and on-disk event-log folder can expose different identifiers. A fresh log alone does not prove that a newly dispatched command reached that session. Do not rewrite authorization to another folder to bypass a mismatch; verify the exact submitted root prompt and dispatch-result session before accepting completion.

## Images and files

Telegram photos and documents are downloaded only after the chat is authorized. Supported extensions are `.jpg`, `.jpeg`, `.png`, `.webp`, `.pdf`, `.txt`, `.csv`, `.docx`, and `.xlsx`. Each file must be nonempty and no larger than 20 MiB; a bridge request accepts at most ten attachments. The trusted storage root is `telegram-attachments` beside the inbox directory. Path containment, regular-file, redirected-directory, and declared-versus-actual size checks run before forwarding. Files with no caption use `Ekteki dosyayı incele.` as the request. Their contents are untrusted data, not instructions that can override approval or safety rules.

## Local VSIX packaging

Install the pinned package dependencies with `npm ci`, run `npm test`, then build a local package with:

```sh
npm run package:vsix -- --out ../../artifacts/<session>/arsangaz-telegram-copilot-bridge-0.2.17.vsix
```

Use a new session artifact directory; do not package into this source folder or install the VSIX as part of a build. `.vscodeignore` is an allowlist for the extension manifest, README, entry point, and its runtime helper modules. Tests, previous VSIX files, dependencies, settings, credentials, and workspace state are excluded.

Workflow waits and HTTP transport timeouts are indefinite unless the operation is explicitly canceled or the application is closing. The 20 MiB attachment limit remains in force. Forwarding a validated path does not guarantee that the selected Copilot model can read every supported format; image and document readability needs a live test.

## Delivery and interactions

The AgentWatcher persists final and failure reports in a local Telegram outbox before attempting delivery. Failed sends remain queued and retry with capped exponential backoff; delivery is never redirected if the authorized chat configuration changes. Telegram API acceptance is logged as delivery accepted, not as proof that the recipient viewed the message. A retry can duplicate already accepted chunks if Telegram accepted them but the process stopped before the local queue entry was removed, or if a multi-chunk send failed partway through.

Session replies whose bridge delivery outcome is unknown remain persisted indefinitely, including across restarts. Elapsed time alone neither discards them nor authorizes sending a possible duplicate. Queue evidence must establish whether the bridge already delivered the correlated reply before the session reporter releases it.

The bridge forwards a supported pending tool approval or question card to the authorized Telegram chat. Approval and rejection buttons are offered only when VS Code supplies a session resource, so the decision can be scoped to the intended chat. Telegram question-card responses support text, single-select, and multi-select answers when the matching VS Code controls can be uniquely identified through Windows UI Automation. If a question/card cannot be matched, a required multi-select is empty, or an unsupported freeform answer is provided, the response fails closed and the user must finish the card in VS Code. Elicitation forms and additional interaction cards that appear later in the same Copilot turn are not currently exposed by VS Code's `blockOnResponse` result and must be completed in VS Code.

After one supported approval or question-card response, the bridge continues waiting for authorized terminal evidence. A card completed directly in VS Code can also release this wait. Required approval/question cards, explicit failures, and final reports remain deliverable; no approval is granted automatically. Later cards and elicitation forms must be completed in VS Code because full multi-interaction relaying is not supported.

The extension uses internal `workbench.action.chat.open` and `blockOnResponse` commands together with authorized local event-log evidence, not a public VS Code response-completion API. Compatibility is limited to VS Code 1.140 or later and must be re-verified after VS Code updates.

## Correlated completion contract

Each completion JSON file is named with the bridge request ID and contains both `id` (bridge request ID) and `taskId` (AgentWatcher job ID), plus `status`, `report`, and `updatedUtc`. AgentWatcher accepts a result only when both identifiers match the waiting request and task. Rebuild and install an updated VSIX, then reload the VS Code window before runtime uses the new extension code.

## Installation

Package the extension with Node.js and the VS Code Extension Manager (`vsce`), then install the generated VSIX:

```powershell
npx --yes @vscode/vsce package --out .\arsangaz-telegram-copilot-bridge-0.2.18.vsix
code --install-extension .\arsangaz-telegram-copilot-bridge-0.2.18.vsix
```

After installation, reload the VS Code window with **Developer: Reload Window** so the new extension code is loaded. The extension installer does not force a reload. Keep the ERP workspace open and confirm the status bar says **Telegram → VS Code Chat hazır**.
